# Security Policy

X-Ray is a browser extension that holds **NOSTR private keys** and runs a
content script on every page you visit. Security reports are taken
seriously here, and reporters are credited unless they'd rather not be.

## Supported versions

Only the latest released version is supported. X-Ray is solo-maintained;
there are no backport branches. Fixes ship in the next tagged release.

| Version | Supported |
| ------- | --------- |
| latest release | yes |
| anything older | no — please update first |

## Reporting a vulnerability

**Please do not open a public issue for a security problem.**

Use GitHub's private vulnerability reporting:
[Report a vulnerability](https://github.com/bryanmatthewsimonson/xray/security/advisories/new).
It's private between you and the maintainer, and it works for people
without write access.

If that isn't available to you, email **manticor@gmail.com** with
`X-Ray security` in the subject line.

Useful to include, to whatever extent you can:

- Affected version (`chrome://extensions` shows it) and browser.
- What an attacker gains — key disclosure, cross-context escalation,
  publishing as someone else, and so on.
- Reproduction steps, or a page that triggers it.

**Never include a real `nsec`, an API key, or a workspace backup file in
a report.** A backup file contains your primary signing key
(see `src/shared/backup.js`). Redacted or synthetic values are fine, and
raw event JSON is fine — a `pubkey` is public by definition.

### What to expect

- Acknowledgement within **7 days**.
- An assessment, and a fix timeline if the report is confirmed, within
  **30 days**.
- Credit in `CHANGELOG.md` and the release notes when the fix ships,
  unless you ask otherwise.

This is a volunteer project with no bounty program.

## Scope

**In scope**

- Anything that discloses private key material (`local_primary_identity`,
  the `local_keys` registry, the user-supplied LLM API key under
  `xray:llm:key`).
- Escaping the isolated world, or a web page reaching extension-privileged
  code — the MAIN-world bridges (`src/page/nip07-bridge.js`,
  `src/page/api-interceptor.js`) and the `web_accessible_resources`
  surface are the interesting parts.
- Signing or publishing a NOSTR event without the user's intent, or as an
  identity the user does not control.
- Supply-chain issues in the build and release pipeline
  (`.github/workflows/`, `esbuild.config.mjs`).
- Injection through captured page content into a reader, side panel,
  portal, or network surface.

**Out of scope**

- Findings that require a browser already compromised at the OS level, or
  physical access to an unlocked machine.
- The `declarativeNetRequest` CSP-strip rule (`rules/csp-strip.json`) as
  such. It is a deliberate, documented trade-off for the YouTube
  transcript fetch — but a way to *abuse* it beyond that purpose is very
  much in scope.
- Relay operators seeing what you publish to them. NOSTR events are
  public by design; that is the protocol, not a defect.
- Third-party platform changes that merely break capture.
- Reports generated by a scanner with no demonstrated impact.

## For users

- Your primary signing key lives in `chrome.storage.local` and never
  leaves your machine unless you export a backup. Treat a backup file
  exactly as you'd treat the key itself.
- Prefer **NIP-07** or **NSecBunker** signing if you'd rather X-Ray never
  hold your key at all.
- Releases are published at
  [Releases](https://github.com/bryanmatthewsimonson/xray/releases) and
  built by [`release.yml`](.github/workflows/release.yml) from a tagged
  commit. Anything offering you an X-Ray build from another source is not
  from this project.
