# Corpus-automation lens — fresh-eyes audit of X-Ray (2026-09-06)

Lens: **corpus capture + claims extraction + entity extraction for hundreds of URLs**, read through the `automator` discipline (`.claude/skills/automator/SKILL.md`) and the `xray-capture` operational skill. Yardstick: wide release to non-technical research groups. Baseline and rules: `BRIEFING.md`. Tree == origin/main `c1e652c`; PR #374 read from `origin/claude/eager-knuth-ipv3xd`.

Invoking moment (automator Protocol step 1): a **proposed automation** — the maintainer's ask names "automation of corpus capture + claims extraction + entity extraction for hundreds of URLs" — plus a **rot sweep** over the automation that already exists.

---

## Verdict

**What works end to end today, at N≈10.** Paste a list of ordinary HTML article URLs into the portal's *Import URLs* panel with "Analyze each imported page" ticked, and X-Ray will fetch each page from the extension origin (`src/shared/url-import.js:190-209`), run Readability on the HTML string (`:140-177`), archive it with the canonical hash (`:277-279`), tag it into the case, and — per page, in the same worker slot — run the ONE article pass (`src/portal/import-urls.js:171-195` → `src/shared/article-pass.js:153-271`), which caches the extract under a content-only key (`src/shared/case-synthesis.js:254-266`) and folds every atom into the durable `article-extractions` record as an `open` proposal (`src/shared/map-artifacts.js:14-16, 250`). The case dashboard then shows per-article folds with *Accept all open (N)* / *Dismiss* / *Link all covered* (`src/portal/extraction-block.js:465-584`), and the reader's Suggest serves the cached extract instantly with entity proposals and a link-or-create ladder (`src/reader/llm-review.js:51-54, 286-293`). The pure core is chrome-free and 733+334+79 lines of node tests cover it (`tests/article-pass.test.mjs`, `tests/url-import.test.mjs`, `tests/extraction-accept-all.test.mjs`). That is real, and better-engineered in the small than most of what I have audited: the cache-key discipline (one unit builder, `case-synthesis.js:29-56`), the grounding firewall, the salvage-on-truncation path (`src/shared/llm-stream.js:63-111`), and the honest disclosure of `truncated` vs `partial` (`article-pass.js:257-270`) are all KEEP.

**What breaks at N=100.** Four things, in harm order. (1) The batch lives in a portal tab's JS closure — nothing persists the URL queue, so a reload, a tab close, a laptop sleep, or a service-worker loss mid-run ends the run silently, and re-running the paste *skips* already-archived rows from analysis (`import-urls.js:139-141`). PR #374 makes an individual in-flight LLM result durable (`llm-jobs.js`), which is the right primitive, but it is not a resumable queue. (2) The one review surface that scales — the portal's *Accept all* — throws away the entity half of the pass: the durable record stores no entities (`map-artifacts.js:95-108`), the portal mints every claim with `about: [caseId]` and nothing else (`extraction-block.js:372-380`), and entity proposals plus claim→entity `about` links exist only transiently in the reader modal, one article at a time (`article-pass.js:283-331`). So "claims + entities for hundreds of URLs, reviewed efficiently" is, today, "claims at scale, entities one tab at a time". (3) Rate limiting is one fixed 15-second retry with no `Retry-After` and no backoff (`src/shared/audit/run-orchestrator.js:50-70`), and three independent drivers each run at concurrency 2 with no shared queue (`import-urls.js`/`url-import.js:248`, `synthesis-block.js:516`, `entity-page.js:415`). (4) Fetch-based import cannot see JS-rendered pages, bot walls, or any platform handler (YouTube/FB/IG/TikTok/Twitter/Substack-API all need a live tab — `src/shared/platforms/index.js:49-92`), and the only live-tab automation is the `#xray:capture` marker driven one URL at a time through a connector that opens an unclosable reader tab per capture (`.claude/skills/xray-capture/SKILL.md:15-26, 89-92`).

**What breaks at N=500.** Everything above, plus: ~5 hours of an open tab at concurrency 2 (see the cost/time table below); backups that include every extract, every record, and the source bytes (`src/shared/backup.js:442`) become hundreds of MB; and the review burden becomes the product — 500 articles × ~40–100 atoms is 20,000–50,000 open proposals rendered as 500 folds in one ~4,400px column with no cross-article sort, no filter, and no use of the `load_bearing` flag the pass already computes (`extraction-block.js` never reads it). The IndexedDB side is fine now that `unlimitedStorage` is requested and the 500-row eviction is off the write path (B1 closed — `archive-cache.js:35-52`).

**Fresh eyes.** The project has already built the hard, correct parts — the content-addressed cache, the durable proposal layer with a review state, the grounding, the merge-import — and then bolted the driver for all of it onto a browser tab, driven by a human's paste, gated by a rule ("never auto-accept into durable data") whose provenance is agent-authored design docs (E5 per the questionnaire's Q11) and which the maintainer's own MA.6 ruling already contradicts in spirit: unreviewed machine output *is* durable, *is* publishable, and the review state is the safeguard. If I started today for research groups I would keep the pure core byte-for-byte, move the driver out of the tab into a persisted job queue (the `llm-jobs.js` shape, extended to URLs), run capture through a Playwright harness that loads the real extension (the `ma6-walk.mjs` shape, which the briefing verified runs in CI-shaped containers), let the pass run outside the browser as a CLI over the same modules with results ingested through the MA.7 merge-import seam that already exists, and make the human's job *triage*, not *acceptance* — with publishing as the one gate the constitution actually names (Art. 8: accountability "attaches to the operator's published record, never as a gate on the pursuit of truth").

## What is good (KEEP)

- **`articleMemberUnit` + `corpusMapRequest` + `corpusExtractKey` — one unit builder, one request builder, one content-only key** (`src/shared/case-synthesis.js:29-56, 233-266`). Pay-once economics are real: an extract is shared across cases, entity pages, the reader, and import. The key deliberately excludes claims and the case frame (corpus-v4/v7). This is exactly the seam a CLI needs.
- **`articleSourceForExtract` reads the archive row, not the reader object** (`article-pass.js:53-65`), with the docblock explaining why (`htmlToMarkdown` is not idempotent). Prevents silent double-pay.
- **The durable proposal layer** (`map-artifacts.js`): span-dedup by overlap fraction, no semantic merge (`:31-36`), `status` on every atom, `producer` stamp, claims-free storage, bounded ledgers (`:38-49`), and a total-function normalizer for foreign rows (`:124-150`). This is the store a scaled review surface should be built on — it just isn't yet.
- **`repairCorpusExtract` before validate, and the two whole-extract refusals** (`case-synthesis.js:562-637`) — the 2026-08-13 poison lesson institutionalized: a wrong-typed list never caches.
- **Streaming + salvage + honest `partial`/`truncated`** (`llm-stream.js:63-111`, `llm-client.js:668-795`, `article-pass.js:257-270`). A cut-off map call yields its complete atoms with the loss disclosed.
- **One paid shape-repair round, never on a truncated payload** (`llm-client.js:718-784`). The human is no longer the retry loop.
- **`ensureArticleExtract`'s injectable IO and `force`** (`article-pass.js:153-198`) — testable without chrome; a poor-but-valid extract can be re-read at full price by choice.
- **PR #374's job runner** (`llm-jobs.js`): result persisted before any response hop, scope-keyed reuse, workspace-scoped, TTL sweep, `lost` never replayed, backup-excluded. This is the correct primitive and it is unit-tested against worker-restart paths (`tests/llm-jobs.test.mjs`, 564 lines).
- **`url-import.js`'s honesty rules** (`:13-27`): thin ≠ failed, PDF is a skip, already-archived is idempotent and re-tags, failures carry messages and the batch continues. The redirect-identity call is recorded (JOURNAL ~4918).
- **The entity resolution ladder at accept time, not in the prompt** (`entity-resolution.js:1-44`): rung labels, no scores, never auto-merge. Keeps the extract cache registry-free.
- **`tools/smoke/ma6-walk.mjs`**: loads the unpacked extension in real headless Chromium, seeds through the extension's own bundled modules (`tools/smoke/seed-entry.js`), pins relays to loopback before anything is clickable. The briefing verified it runs end to end in this container. It is the proof that browser-level automation of this extension is not hypothetical.
- **The AW agent-walk rows** (`docs/SMOKE_TEST.md:1639-1669`) with the agent-verifiable criterion stated and a real ledger row (`:36`).
- **The `#xray:capture` marker's DOM stamp** (`src/content/index.js:157-190`): flag-gated, inert by default, outcome readable from ordinary page context, `hashchange` covered.

## Grandfathered

- **"Never auto-accept — every LLM proposal is human-accepted into durable data."** Grandfathered by `docs/PHASE_14_5_LLM_ASSIST_KICKOFF.md §4` → `docs/CASE_SYNTHESIS_DESIGN.md:129` ("No auto-accept / no auto-publish. Every mutation is a human click") → `DISCIPLINES.md §15.3` ("One accept per artifact — bulk credulity is not review", E5 per questionnaire Q11) → the xray-capture skill's hard rule 1 → the automator skill's Standard 10 never-automate list ("acceptance of any LLM suggestion into durable data"). The premise is gone twice over: (a) MA.1 made unreviewed atoms durable (`map-artifacts.js:14-16`), and (b) the maintainer's MA.6 ruling (JOURNAL 2026-07-29) publishes the whole unit, unreviewed atoms included, with the review state as the safeguard. The rule now governs only the *claim-registry mint* — and even there `Accept all` ships. The constitution itself never states it (see CORP-7).
- **The portal tab as the batch driver.** Grandfathered by Phase 28.1's design choice ("without a tab per page: fetch each URL from the extension page", `url-import.js:3-11`) — correct for "no tab per page", but it made the *portal page* the orchestrator, and 28.2/UA.3 then hung the analysis on the same closure. The premise ("a paste of ~20 worksheet URLs", JOURNAL ~4918-4941, the eggs worksheet) does not hold at hundreds.
- **One URL at a time through the claude-in-chrome connector.** Grandfathered by the connector's limits verified 2026-07-16 (`SKILL.md:15-26`). Those limits are the connector's, not the browser's; Playwright has none of them (ma6-walk reaches `chrome-extension://` pages directly, `ma6-walk.mjs:72-85`).
- **`concurrency: 2` "polite to origins"** (`url-import.js:223, 248`) reused as the LLM concurrency (`import-urls.js:171-195` runs the pass in the same slot). Origin politeness and API throughput are different budgets grandfathered into one number.
- **`pending-suggestions` store** — kept "no DB migration" after UA.3 retired parking (JOURNAL ~1382-1390). Dead weight with a rationale.
- **The `$3/$15` Sonnet 5 pricing note and the "~$0.50 vs ~$0.80 per episode" derivation** (`llm-prompts.js:35-38, 85-91`) — grandfathered by the 2026-08 price sheet; current first-party pricing is $2/$10 for Sonnet 5 (cached skill table 2026-06-24). The derivation's *conclusion* (Sonnet 5 as default) still holds; its numbers are stale.

## Findings (ranked by harm)

### CORP-1 · The batch is a tab closure: no persisted queue, no resume, and a re-run skips the un-analyzed rows
- **Harm:** 5 · **Class:** DEFECT · **Effort:** M · **ROAD_TO_1_0:** none (new; #374 is adjacent)
- **Evidence:** `src/portal/import-urls.js:134-244` (the whole run is one click handler's `await importUrlList(...)`); `src/shared/url-import.js:294-312` (`orchestrateModuleRuns` over an in-memory list, results in a `Map`); `import-urls.js:139-141` ("Already-archived rows are skipped — use the case dashboard's Pre-analyze to analyze those"); `llm-jobs.js:14-30` (#374 persists ONE pass result under a job id; nothing persists the list of URLs or which ones are done); `llm-jobs.js:53-55` (`LLM_JOB_PASSES` is three passes, no `url-import`).
- **Claim:** At N=100 (≈60–100 min at concurrency 2, see CORP-5), the probability that the portal tab survives untouched is low; when it does not, the run stops with no record of where, `already-archived` rows are then excluded from analyze-after-import, and the user must discover the case dashboard's Pre-analyze to finish. Nothing is *lost* (the archive rows and cached extracts survive) but nothing *resumes*.
- **Fresh-eyes action:** Extend the #374 job pattern from "one LLM call" to "one batch": a `corpus-intake` job record in `chrome.storage.local` holding `{urls[], cursor, perRow{status}}`, driven from the service worker (fetch is legal there — `host_permissions <all_urls>`, `manifest.json:53-60`; the SW already fetches for arXiv, `platforms/index.js:83-88`) with the page as a viewer that attaches by scope key and can close. `DOMParser` is unavailable in a worker; the Readability step needs either an offscreen document (`chrome.offscreen`, MV3) or stays page-side while the queue and LLM stage move to the worker — the honest split is: queue + fetch + LLM in the worker, extraction in an offscreen document. Resume = re-read the record on worker boot (the runner already sweeps on boot, `llm-jobs.js:263-278`).

### CORP-2 · The scalable review surface drops the entity half of the pass
- **Harm:** 5 · **Class:** DEFECT · **Effort:** M · **ROAD_TO_1_0:** none
- **Evidence:** `src/shared/map-artifacts.js:95-108` (`emptyRecord`: assertions, sources, open_questions, positions — no `entities`, no per-atom `about`); `src/shared/map-artifacts.js:187-260` (`mergeExtractIntoRecord` folds atoms only); `src/portal/extraction-block.js:372-380` (`acceptOne` → `ClaimModel.create({... about: [caseId].filter(Boolean) ...})`); `src/shared/article-pass.js:283-331, 377-400` (entity proposals and `about` refs are built for the *modal* from the raw extract); `src/reader/llm-review.js:51-54, 210-293` (the ladder lives in the reader modal only).
- **Claim:** The one pass produces claims, entities, and claim→entity links (corpus-v9, `corpus-prompts.js:107`). The durable layer keeps the claims. The entities and links survive only in the fingerprint cache (`corpus-extracts`) and are rendered only by the per-article reader modal. A researcher who reviews 100 articles from the case dashboard gets 100 articles' claims with no entity tags and no `about` links beyond the case itself — the knowledge graph the pass paid for never materializes unless every article is also opened in the reader.
- **Fresh-eyes action:** Fold `entities` (name, type, mention, grounded span, status) and per-atom `about` refs into the `article-extractions` record (schema-evolution review: additive field, `xray-audits` v8, normalizer at `map-artifacts.js:150`), and give the portal an entity review fold that runs the same ladder (`rankEntityCandidates`) so `Accept all` mints claims WITH their `about` links resolved by identity rungs and leaves near-name rungs as the human's pick. Until then, label the portal's Accept-all honestly: "mints claims without entity links".

### CORP-3 · Capture at scale has three paths and none scales past a worksheet
- **Harm:** 4 · **Class:** GAP · **Effort:** L · **ROAD_TO_1_0:** B8 (open), T4 MA-rows (open)
- **Evidence:** `src/shared/url-import.js:190-209` (a plain `fetch`; no JS execution, no interstitial detection, `credentials: 'include'` only); `:140-177` (`extractWebArticle` — `contentType: 'article', platform: null`; no `captureForPlatform`); `src/shared/platforms/index.js:49-92` (YouTube/Twitter/TikTok/Instagram/Facebook are `synthesize`-only from a live DOM; Substack/PMC/arXiv enrich a live DOM); `src/shared/content-detector.js:13-49` (detection reads `document`); `.claude/skills/xray-capture/SKILL.md:15-26` (connector cannot reach extension pages), `:89-92` (a reader tab per capture, unclosable), `:3` (sequential, one URL at a time); `tools/smoke/ma6-walk.mjs:61-73` (Playwright loads the unpacked extension and reaches `chrome-extension://` pages); BRIEFING addendum (it ran here, ~2 min).
- **Claim:** Fetch import covers static HTML only; the marker path covers everything the extension can capture but at ~10 s/URL serial with a tab per capture and a human flipping a flag; there is no path that captures a YouTube transcript, a tweet, or a Cloudflare-walled article in batch. For a COVID-casework corpus (preprints, news, YouTube, Substack, tweets) that is most of the corpus.
- **Fresh-eyes action:** Build **one** Playwright harness (`tools/harness/capture.mjs`) reusing `ma6-walk.mjs`'s launch block: for each URL open a tab, navigate to `<url>#xray:capture` (flag pre-set in the profile through the seed harness, `seed-entry.js`), wait for `dataset.xrayCaptured`, read the reader tab's archive result through `chrome-extension://` page evaluation, close both tabs, next. It runs every platform handler, can hold a logged-in profile (`launchPersistentContext`), detects interstitials with the skill's title/len heuristics (`SKILL.md:74-80`), and is agent-runnable in CI. Keep fetch import as the fast path for static pages (it is 10× cheaper) and route by `content-detector`-shaped URL rules: known platform hosts → harness, else fetch first, harness on `thin`/interstitial.

### CORP-4 · Rate-limit handling is one fixed 15 s retry across three uncoordinated drivers
- **Harm:** 4 · **Class:** DEFECT · **Effort:** S · **ROAD_TO_1_0:** none
- **Evidence:** `src/shared/audit/run-orchestrator.js:9-11, 50-70` (retryable = 429/5xx/timeout; one retry; fixed `retryDelayMs`); `src/shared/llm-client.js:154-156` (429 → a string, `Retry-After` never read); `src/shared/url-import.js:248-249, 294-312` (concurrency 2, 15 s); `src/portal/synthesis-block.js:516` and `src/shared/entity-page.js:415` (each concurrency 2, independent pools); JOURNAL 2026-09-05 (five passes "still on the held-open shape").
- **Claim:** Per-tier Anthropic limits are tokens-per-minute as well as requests-per-minute (tier-dependent; not verified from here). A 100-article run at 2–3 in flight, each sending ~3–100k input tokens and producing ~3–10k output tokens, will hit a low-tier OTPM/ITPM ceiling in bursts; the second attempt after a flat 15 s hits it again; the row is marked `failed` and the run moves on. Two surfaces run at once (a Pre-analyze while an import is analyzing) double the burst. The failure is honest but the recovery is manual.
- **Fresh-eyes action:** In `postMessages`, surface `Retry-After` (and `anthropic-ratelimit-*-reset` headers) on the 429 result; in the orchestrator, exponential backoff with jitter capped at ~2 min and up to 4 attempts for 429 only; one shared SW-side semaphore for all `corpus-map` jobs (the #374 runner is the natural owner — a `maxConcurrent` on `createLlmJobRunner`), so every driver queues through it.

### CORP-5 · Cost and time are unmeasured: usage is returned and dropped, the dialog counts calls not dollars, and the price note is stale
- **Harm:** 4 · **Class:** GAP · **Effort:** S · **ROAD_TO_1_0:** none
- **Evidence:** `src/shared/llm-client.js:789-795` (`usage: data && data.usage` returned); `src/shared/article-pass.js:252-255` (`saveExtract({key, extract, model, cachedAt, partial})` — no usage); `src/portal/import-urls.js:139-141` ("up to N calls"); `src/shared/llm-prompts.js:35-38, 85-91` ($3/$15; "~$0.50 vs ~$0.80 per episode"); measured prompt overhead: map system 1,906 chars + tool schema 3,269 chars + user wrapper 47 chars ≈ 5.2k chars ≈ 1.4k tokens per call (run from `corpus-prompts.js` in this container); `MAX_MEMBER_INPUT_CHARS = 400000`, `MAX_MAP_OUTPUT_TOKENS = 64000` (`corpus-prompts.js:132, 146`); no `cache_control`, no `output_config.effort` anywhere (`grep` over `llm-client.js`: 0 hits); adaptive thinking is on by default on Sonnet 5 / Opus 5 / Fable 5 and billed as output, "not re-measured" (`llm-prompts.js:38-44`).
- **Claim — estimate per 100 articles, one-article pass, current prompts** (an estimate; declared and derived, Art. 5.2 — inputs are the prompt sizes above, article lengths assumed, output ratio assumed from "comprehensive atomization: verbatim quote + paraphrase + entities", which roughly re-emits the source text once):

  |---|---|---|---|---|---|---|
  | Median news/blog, ~1,200 words | ~3.2k | ~4–5k | ~$0.05 | ~$0.13 | ~$0.28 | ~60–90 s |
  | Long-form, ~5,000 words | ~9.5k | ~9–12k | ~$0.13 | ~$0.32 | ~$0.70 | ~2.5–4 min |
  | Transcript at the 400k bound | ~100k | ~20–30k | ~$0.45 | ~$1.15 | ~$2.50 | ~6–10 min |
  | **100 mixed (70/25/5)** | | | **≈ $9–12** | **≈ $23–30** | **≈ $48–65** | **≈ 45–75 min serial; ≈ 25–40 min at 2 in flight if no 429s** |

  Add ~5–10% for shape-repair rounds (`llm-client.js:718-784`) and 429 retries. At N=500: ~$45–60 on Sonnet 5, ~2–3 h at 2 in flight, 4–6 h serial. None of this is visible to the user before or after a run: the confirm dialog cannot say "≈ $10", and nothing in storage lets anyone reconcile a bill.
- **Fresh-eyes action:** Persist `usage` on the cached extract and on the job record; sum it in the import panel and the case dashboard ("this corpus has cost $X across N calls, M cached"); state a pre-run estimate from character counts with the derivation shown (Art. 5.2 conditions 1–3); fix the price note or, better, remove hardcoded prices and show tokens. Prompt caching is *not* the lever here — the stable prefix (~1.4k tokens) is at or under the model minimum cacheable prefix, so gains would be marginal; `output_config.effort: "low"` on the map pass is the lever to measure (extraction against supplied text is exactly the shape the roster note says needs no deep reasoning, `llm-prompts.js:85-91`).

### CORP-6 · Review at 5,000 proposals has no triage: per-article folds, no sort, no filter, `load_bearing` unused, sequential read-modify-write accepts
- **Harm:** 4 · **Class:** GAP · **Effort:** M · **ROAD_TO_1_0:** T8 "consolidate import/export verbs" (open) is adjacent; the ux lens owns the dashboard
- **Evidence:** `src/portal/extraction-block.js:335-338` (partition per record), `:465-508` (Accept-all is per article, runs `acceptOne` sequentially, each a read-modify-write of the whole record — `:347-365`); `extraction-block.js` never references `load_bearing` (grep: 0); `src/shared/case-synthesis.js:282-287` (`loadBearingSubset` exists for the reduce only); BRIEFING addendum (dashboard = one ~4,400px column of folded sections, each with a 3–5 line explainer before any control); `docs/DISCIPLINES.md:539` ("One accept per artifact — bulk credulity is not review").
- **Claim:** At 100 articles the human faces ~4,000–10,000 open atoms; the tools are "open each fold, read, Accept all or Dismiss per row". There is no corpus-wide list sorted by load-bearing-first, no filter by entity, no "accept the load-bearing subset", no keyboard flow, and the doctrine text says bulk acceptance is not review while the button says Accept all. The honest description of what the human can *actually* do at this scale is: accept everything without reading, or not finish.
- **Fresh-eyes action:** Make triage the unit of work, not acceptance: one corpus-wide proposal table over the `article-extractions` store (already keyed and statused) with columns quote / paraphrase / article / load_bearing / entities-mentioned / status, default sort load_bearing→article, filters by entity and article, bulk *state* changes (`open`→`accepted`|`dismissed`|`deferred`) with one batched store write per record, and "Accept all load-bearing across the case" as the headline action. The per-article folds stay as the drill-down. This needs CORP-7's ruling first, because "what accept means" is the open question.

### CORP-7 · "Every proposal is human-accepted" is agent-derived and now inconsistent with the durable layer, MA.6, and the shipped buttons — the constitution names publishing, grounding, and marking, not acceptance
- **Harm:** 3 · **Class:** GRANDFATHERED · **Effort:** S (a ruling) · **ROAD_TO_1_0:** none; questionnaire Q11, F8
- **Evidence:** `docs/CONSTITUTION.md` Art. 4.1 (evidence-bound: "followable citation of a captured artifact" — grounding satisfies this mechanically, `map-artifacts.js:485-491`), Art. 4.7 (method/prompt versions/coverage published — the record stores model + prompt version), Art. 5.2 cond. 4 (an estimation "never automatically triggers a consequence"), Art. 6 (never-merge — the ladder never auto-merges, `entity-resolution.js:11-31`), Art. 8 (accountability "attaches to the operator's **published record**, never as a gate on the pursuit of truth … a pre-publication gate heavy enough to matter would stop meaningful truth-seeking"); JOURNAL 2026-07-29 (MA.6: "the WHOLE unit publishes — every atom in every review state … the marking is now the only safeguard"); `map-artifacts.js:14-16` (unreviewed atoms durable since MA.1); `CASE_SYNTHESIS_DESIGN.md:129`, `DISCIPLINES.md:539`, `xray-capture/SKILL.md:29-33`, `automator/SKILL.md:190-198` (the rule's four homes, all agent-authored); questionnaire Q11 ("E5 per clause", "Either §15.3 means something narrower than it says, or the product violates its statute").
- **Claim:** Nothing in the constitution requires a human click before an LLM proposal is stored locally; the constitution requires grounding, provenance, spread/disclosure, never-merge, and a truthful published record. ## Fresh-start design

If I started X-Ray's corpus pipeline today for research groups, keeping what is genuinely good:

**Layer 1 — capture at scale.** One Playwright harness that loads the real extension (`ma6-walk.mjs`'s launch, persistent profile so logins survive), fed by a URL file, that: (a) tries fetch-import first for hosts with no platform handler and accepts the result only if it passes the interstitial tells; (b) otherwise opens a tab with `<url>#xray:capture`, waits for the stamp, reads the archive outcome from the extension page, closes the tabs; (c) writes a per-URL result table. It runs the content script, every platform handler, the transcript fetch, and the PDF route — unchanged. It is agent-runnable in CI against a fixture site, and runnable by a researcher with `npm run capture -- urls.txt`. Options considered: **fetch-only** (exists; keep as the fast path — cheap, no browser, but blind to JS/platforms/walls); **native-messaging/companion capture service** (a Python service like the transcriber owning a headless browser — rejected for now: it re-implements what the harness gets for free by loading the extension itself, adds an install step the companion already shows is a support burden, and the constitution's "behaves exactly as before when absent" contract would have to be re-proven); **Playwright harness driving the real extension** — **recommended**: reuses proven code, every capture is a real capture, and the same harness is the CI smoke.

**Layer 2 — extraction at scale.** The `llm-jobs.js` runner becomes the one queue: a `corpus-intake` job type holding URLs + cursor + per-row status, a shared concurrency semaphore, `Retry-After`-aware backoff, usage persisted per result, cost shown before and after. Does #374 give this? It gives the durable-result primitive and the scope-key dedupe — the right foundation — but not the queue, the resume, the shared concurrency, or the cost accounting. **Outside the browser**: a CLI over the same modules (CORP-8) for the researcher who wants to run 500 articles overnight from a terminal or from CI, with results ingested through Import & merge (MA.7 re-grounding makes the foreign records safe). Both paths share one cache key, so nothing is paid twice. Model default stays Sonnet 5; measure `effort: "low"` on the map.

**Layer 3 — review at scale.** Triage, not acceptance. The `article-extractions` store already has `status` per atom; give it `entities` (CORP-2) and build one corpus-wide table with sort/filter/bulk-state. "Accept" = a human-set state; minting a 30040 claim from an accepted atom is mechanical; *publishing* is the human gate (Art. 8), and entity *merge* stays a per-item human pick (Art. 6). What "a human accepts every proposal" means at 5,000 proposals is, honestly: the human accepts the load-bearing ~10–15% after reading them, marks the rest `deferred`, and the published 30070 discloses all of it with states — exactly the MA.6 posture, applied to the local record too.

**Phased plan (first slice agent-runnable in CI):**
1. **Slice 0 (S, agent-runnable, CI):** `playwright` devDependency; fix `ma6-walk.mjs` paths + selector; CI job `smoke-browser`; TOIL.md seeded. Closes B8's mechanics.
2. **Slice 1 (M):** `tools/harness/capture.mjs` — marker-driven capture of a URL file through the loaded extension; fixture-site CI test that captures one static page, one SPA, one PDF and asserts archive rows. Manual path stays: Import URLs and the toolbar.
3. **Slice 2 (M):** shared runner concurrency + `Retry-After` backoff + usage persisted + cost line in the confirm dialog. Unit-tested against the job stub.
4. **Slice 3 (M, needs Q1 ruling):** `entities` on the durable record + portal entity fold with the ladder; corpus-wide triage table; bulk state changes.
5. **Slice 4 (M):** `corpus-intake` job type in the SW with resume; the portal panel becomes a viewer.
6. **Slice 5 (M, needs security review):** CLI article pass over an esbuild node bundle; documented export → run → import & merge round trip.

Maintainer decisions needed before slices 3–5: Questions 1–4 below.
