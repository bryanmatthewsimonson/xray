## 2026-11-06 — `depends-on` joins the kind-30055 vocabulary (claim dependency D.1)

**Tags:** wire, design, one-way-door

**Decision.** A new value of the kind-30055 `relationship` tag,
`depends-on`: directional, source depends on target, hashed in
semantic order like `supports`. It is the first slice of
`docs/CLAIM_DEPENDENCY_DESIGN.md` (PR #432): the necessary-condition
edge the maintainer asked for after earlier attempts to show
load-bearing arguments "have been done poorly". Additive on an active
kind (ecosystem-pm standard 2): no tag moves, no `d` derivation
changes, and every existing wire fixture regenerates byte-identical.

**Why a 30055 value and not a local store.** The maintainer chose it
in conversation (design §8): a dependency is as publishable as
`supports`, and a 30055 link already rides the link modal, the
dossier collector, backup, sync and the counterfactual. The
alternative, a local edge store like the hypothesis map's, would have
needed its own backup, merge and sync paths and still wanted a wire
kind later. A separate NEW kind was not considered: the edge has the
same two endpoints and the same `d` idiom as every other 30055 link.

**Why its own constant.** `DEPENDENCY_RELATIONSHIPS` sits beside
`CLAIM_RELATIONSHIPS` and `REVISION_RELATIONSHIPS` rather than inside
the first, because `EVIDENCE_RELATIONSHIPS` (the reader's link picker)
IS `CLAIM_RELATIONSHIPS`, and the picker may not offer `depends-on`
until slice D.3 adds the authoring test ("could the source still be
true if the target turned out false? then it is `supports`"). A
`depends-on` drawn where `supports` was meant makes the later cascade
lie, so the UI waits for the guard.

**What this slice renders, and what it does not.** The builder, the
local linker, the parser and the ordinary 30055 publish path accept
the value. A stored `depends-on` link already shows GENERICALLY
wherever links render by label: the reader claim card draws "⤵
Depends on →/←" from the linker's label and icon tables, and the
portal library, the entity graph, the sidepanel feed and the Network
queue display relay-fetched 30055 events with whatever `relationship`
value they carry. What does NOT exist yet is every surface that gives
the edge its meaning: the case view's related-link set and the
dossier collector still list `supports`/`updates`/`duplicates` only,
so no cascade, no load-bearing count and no dependency badge until
D.2–D.4. The only producer today is the Network client's
incorporation path, which before this slice refused the value at
`EvidenceLinker.create` and now stores it.

**Compatibility.** An older X-Ray's local store refuses an incoming
`depends-on` at `EvidenceLinker.create`, so the Network queue lists
it as a proposal whose Accept fails with "Invalid relationship"; its
portal library, entity graph and sidepanel feed render the relay
event generically, as they do any 30055 value, with `depends-on` as
the row title or the edge tooltip. Nothing is misattributed and
nothing is stored. `docs/NIP_DRAFT.md` §30055 now lists the value and
states the consumer rule for an unrecognized one in terms that match
this behavior: do not store or interpret, display of the raw value
allowed.

## 2026-11-06 — Proposal and link keys keep endpoint order for directional relationships

**Tags:** design, synthesis

**The bug.** `proposalKey` and `linkRecordKey` sorted the two claim ids
for every relationship, so "A supports B" and "B supports A" were one
key. Two consequences: a dismissed proposal in one direction silently
hid a later proposal in the other, and an existing `supports` link in
one direction made the standalone links pass reject a proposal for the
reverse as "already exists". Claim dependency D.5 made this
load-bearing — "A depends on B" and "B depends on A" are two claims
about the world, and a corpus with both is a circular premise the
cascade must be able to show.

**The fix.** One `pairKey(a, b, relationship)`: endpoints sort only
for a SYMMETRIC relationship (`contradicts`, `duplicates`), under the
old `rel:` prefix; a directional one (`supports`, `updates`,
`depends-on`, the `revision/*` values) keeps order under a NEW
`rel-dir:` prefix. The prefix matters: without it, a legacy sorted key
written for "c2 supports c1" (`rel:c1|c2:supports`) would equal the
new ordered key for "c1 supports c2" and falsely mark it triaged —
the very bug the change removes, kept alive for every legacy entry.

**The cost, stated.** The brief's triage record and the links run's
triage are keyed by these strings. A directional proposal dismissed
before this change was stored under the legacy key; after it, the
same proposal computes a `rel-dir:` key, finds no entry, and
reappears as open — once, in either direction. Re-dismissing it
writes the new key. No migration rewrites stored keys: the legacy
entries can match nothing new (different prefix), so they are inert,
and a rewrite would have to guess which direction a sorted key meant.
Symmetric proposals are unaffected.

**Not changed.** The wire `d` tag of a kind-30055 event already hashed
directional relationships in semantic order (NIP_DRAFT §30055); this
brings the local proposal identity in line with the wire identity.
## 2026-11-12 — Agent-skills configuration: GitHub Issues, the existing `triage` label, and no `docs/adr/`

**Tags:** process, design

**What.** `CLAUDE.md` gains an `## Agent skills` section and
`docs/agents/` gains three files (`issue-tracker.md`,
`triage-labels.md`, `domain.md`). They tell the plugin engineering
skills (triage, tickets, wayfinding, domain modeling) where issues
live, what the triage labels are called here, and where the domain
docs and decision records are. No code, test or guard changes.

**The friction it answers.** On 2026-11-12 the maintainer asked for
one coordinating session over all X-Ray work, because uncoordinated
sessions "could clash". The survey that followed found the conditions
for it already in place: every desktop session shared one checkout
with no worktree; the four-PR cap was full, two of the four
conflicting; a retrieval kickoff had been drafted on one-index-per-
workspace rails that the maintainer's direction of the same day
reverses; and merges were landing from sessions the machine could not
list. The map of who was doing what existed only in session
transcripts. An issue tracker the skills can read and write is where
that map goes, and these files are what the skills need before they
can use it.

**Decisions worth second-guessing.** The maintainer approved the
draft in conversation on 2026-11-12 ("Yes, write it"). Each item is
an INTERPRETATION with its default, not a ruling.
- Issues live in GitHub Issues, and PRs are not a request surface.
  Default: keep. The eight open issues are all from the
  userscript-parity era and want triage or closing.
- The `needs-triage` role maps to the existing `triage` label
  instead of a new `needs-triage`. Default: keep, one label per
  role. Three labels were created on GitHub the same day:
  `needs-info`, `ready-for-agent`, `ready-for-human`.
- No `docs/adr/`. Where a skill says "ADR", `docs/agents/domain.md`
  sends it to the records the repo already keeps: the constitution,
  the rulings ledger, the design docs and this journal. Default:
  keep one decision record. A second, parallel one would split the
  grep this journal exists to make reliable.
- `GLOSSARY.md` goes at the repo root, where the skills look, and
  is not created here; the domain-modeling skill creates it when a
  term is actually resolved. The root is also what `web-ext`
  packages, so the PR that creates it must add it to
  `webExt.ignoreFiles`, or `check:package` fails it as an
  unclassified file. `docs/agents/domain.md` says so.

**Not done.** The eight stale issues are untouched and no map issue
exists. The `wayfinder:*` labels are not created; the wayfinding
skill needs them before its first map.
