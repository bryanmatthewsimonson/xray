## 2026-11-06 — `depends-on` joins the kind-30055 vocabulary (claim dependency D.1)

**Tags:** wire, design, one-way-door

**Decision.** A new value of the kind-30055 `relationship` tag,
`depends-on`: directional, source depends on target, hashed in
semantic order like `supports`. It is the first slice of
`docs/CLAIM_DEPENDENCY_DESIGN.md` (PR #432): the necessary-condition
edge the maintainer asked for after earlier attempts to show
load-bearing arguments "have been done poorly". Additive on an active
kind (ecosystem-pm standard 2): no tag moves, no `d` derivation
changes, and every existing wire fixture regenerates byte-identical.

**Why a 30055 value and not a local store.** The maintainer chose it
in conversation (design §8): a dependency is as publishable as
`supports`, and a 30055 link already rides the link modal, the
dossier collector, backup, sync and the counterfactual. The
alternative, a local edge store like the hypothesis map's, would have
needed its own backup, merge and sync paths and still wanted a wire
kind later. A separate NEW kind was not considered: the edge has the
same two endpoints and the same `d` idiom as every other 30055 link.

**Why its own constant.** `DEPENDENCY_RELATIONSHIPS` sits beside
`CLAIM_RELATIONSHIPS` and `REVISION_RELATIONSHIPS` rather than inside
the first, because `EVIDENCE_RELATIONSHIPS` (the reader's link picker)
IS `CLAIM_RELATIONSHIPS`, and the picker may not offer `depends-on`
until slice D.3 adds the authoring test ("could the source still be
true if the target turned out false? then it is `supports`"). A
`depends-on` drawn where `supports` was meant makes the later cascade
lie, so the UI waits for the guard.

**What this slice renders, and what it does not.** The builder, the
local linker, the parser and the ordinary 30055 publish path accept
the value. A stored `depends-on` link already shows GENERICALLY
wherever links render by label: the reader claim card draws "⤵
Depends on →/←" from the linker's label and icon tables, and the
portal library, the entity graph, the sidepanel feed and the Network
queue display relay-fetched 30055 events with whatever `relationship`
value they carry. What does NOT exist yet is every surface that gives
the edge its meaning: the case view's related-link set and the
dossier collector still list `supports`/`updates`/`duplicates` only,
so no cascade, no load-bearing count and no dependency badge until
D.2–D.4. The only producer today is the Network client's
incorporation path, which before this slice refused the value at
`EvidenceLinker.create` and now stores it.

**Compatibility.** An older X-Ray's local store refuses an incoming
`depends-on` at `EvidenceLinker.create`, so the Network queue lists
it as a proposal whose Accept fails with "Invalid relationship"; its
portal library, entity graph and sidepanel feed render the relay
event generically, as they do any 30055 value, with `depends-on` as
the row title or the edge tooltip. Nothing is misattributed and
nothing is stored. `docs/NIP_DRAFT.md` §30055 now lists the value and
states the consumer rule for an unrecognized one in terms that match
this behavior: do not store or interpret, display of the raw value
allowed.
