## 2026-11-06 — `depends-on` joins the kind-30055 vocabulary (claim dependency D.1)

**Tags:** wire, design, one-way-door

**Decision.** A new value of the kind-30055 `relationship` tag,
`depends-on`: directional, source depends on target, hashed in
semantic order like `supports`. It is the first slice of
`docs/CLAIM_DEPENDENCY_DESIGN.md` (PR #432): the necessary-condition
edge the maintainer asked for after earlier attempts to show
load-bearing arguments "have been done poorly". Additive on an active
kind (ecosystem-pm standard 2): no tag moves, no `d` derivation
changes, and every existing wire fixture regenerates byte-identical.

**Why a 30055 value and not a local store.** The maintainer chose it
in conversation (design §8): a dependency is as publishable as
`supports`, and a 30055 link already rides the link modal, the
dossier collector, backup, sync and the counterfactual. The
alternative, a local edge store like the hypothesis map's, would have
needed its own backup, merge and sync paths and still wanted a wire
kind later. A separate NEW kind was not considered: the edge has the
same two endpoints and the same `d` idiom as every other 30055 link.

**Why its own constant.** `DEPENDENCY_RELATIONSHIPS` sits beside
`CLAIM_RELATIONSHIPS` and `REVISION_RELATIONSHIPS` rather than inside
the first, because `EVIDENCE_RELATIONSHIPS` (the reader's link picker)
IS `CLAIM_RELATIONSHIPS`, and the picker may not offer `depends-on`
until slice D.3 adds the authoring test ("could the source still be
true if the target turned out false? then it is `supports`"). A
`depends-on` drawn where `supports` was meant makes the later cascade
lie, so the UI waits for the guard.

**What this slice renders, and what it does not.** The builder, the
local linker, the parser and the ordinary 30055 publish path accept
the value. A stored `depends-on` link already shows GENERICALLY
wherever links render by label: the reader claim card draws "⤵
Depends on →/←" from the linker's label and icon tables, and the
portal library, the entity graph, the sidepanel feed and the Network
queue display relay-fetched 30055 events with whatever `relationship`
value they carry. What does NOT exist yet is every surface that gives
the edge its meaning: the case view's related-link set and the
dossier collector still list `supports`/`updates`/`duplicates` only,
so no cascade, no load-bearing count and no dependency badge until
D.2–D.4. The only producer today is the Network client's
incorporation path, which before this slice refused the value at
`EvidenceLinker.create` and now stores it.

**Compatibility.** An older X-Ray's local store refuses an incoming
`depends-on` at `EvidenceLinker.create`, so the Network queue lists
it as a proposal whose Accept fails with "Invalid relationship"; its
portal library, entity graph and sidepanel feed render the relay
event generically, as they do any 30055 value, with `depends-on` as
the row title or the edge tooltip. Nothing is misattributed and
nothing is stored. `docs/NIP_DRAFT.md` §30055 now lists the value and
states the consumer rule for an unrecognized one in terms that match
this behavior: do not store or interpret, display of the raw value
allowed.

## 2026-11-06 — Proposal and link keys keep endpoint order for directional relationships

**Tags:** design, synthesis

**The bug.** `proposalKey` and `linkRecordKey` sorted the two claim ids
for every relationship, so "A supports B" and "B supports A" were one
key. Two consequences: a dismissed proposal in one direction silently
hid a later proposal in the other, and an existing `supports` link in
one direction made the standalone links pass reject a proposal for the
reverse as "already exists". Claim dependency D.5 made this
load-bearing — "A depends on B" and "B depends on A" are two claims
about the world, and a corpus with both is a circular premise the
cascade must be able to show.

**The fix.** One `pairKey(a, b, relationship)`: endpoints sort only
for a SYMMETRIC relationship (`contradicts`, `duplicates`), under the
old `rel:` prefix; a directional one (`supports`, `updates`,
`depends-on`, the `revision/*` values) keeps order under a NEW
`rel-dir:` prefix. The prefix matters: without it, a legacy sorted key
written for "c2 supports c1" (`rel:c1|c2:supports`) would equal the
new ordered key for "c1 supports c2" and falsely mark it triaged —
the very bug the change removes, kept alive for every legacy entry.

**The cost, stated.** The brief's triage record and the links run's
triage are keyed by these strings. A directional proposal dismissed
before this change was stored under the legacy key; after it, the
same proposal computes a `rel-dir:` key, finds no entry, and
reappears as open — once, in either direction. Re-dismissing it
writes the new key. No migration rewrites stored keys: the legacy
entries can match nothing new (different prefix), so they are inert,
and a rewrite would have to guess which direction a sorted key meant.
Symmetric proposals are unaffected.

**Not changed.** The wire `d` tag of a kind-30055 event already hashed
directional relationships in semantic order (NIP_DRAFT §30055); this
brings the local proposal identity in line with the wire identity.

## 2026-11-14 — The content-changed banner fired on every video re-capture: a view count, and the same words in other paragraphs

**Tags:** bug, reader, youtube

Field report (maintainer, 2026-11-14, the first build carrying the
2026-10-17 banner change): a YouTube video captured again two days
later raised "Content changed since your last capture" with most of
the transcript marked, and "the majority of the detected differences
are near the timestamp breaks". No word of the transcript had
changed. Two causes, each reproduced against `diffBodies` before the
fix.

1. **The header's view count.** The 2026-10-17 filter knew
   "1,204 views", the order a page writes it. The platform composers
   write the capture header label-first, `**Views**: 1,204` (YouTube:
   Views; TikTok: Views, Likes, Comments, Shares; Instagram: Likes,
   Comments, Views; Facebook: Reactions, Comments, Shares), so that
   line differed on every re-capture. Instagram's `N posts` was not a
   counted word either.
2. **Paragraph breaks.** A transcript's paragraphs are X-Ray's own.
   `coalesceCuesIntoParagraphs` glues caption cues together, breaks at
   the first cue that ends a sentence past 380 characters, and stamps
   each paragraph with its first cue's time. The two captures got the
   same words in cues cut at other points, so a sentence that opened
   the 0:56 paragraph in one closed the 0:25 paragraph in the other,
   and the next paragraph's stamp moved to 1:00. The comparison lined
   up paragraph against paragraph, so both counted as edited. The
   2026-10-17 entry named a re-chunked transcript and accepted it as a
   change; in use it is the common case.

Not established: why the cues were cut differently. Which transcript
strategy each capture used (the signed-URL fetch, the `get_transcript`
hook, the DOM scrape) is on the archived rows and was not read.

Fix (`src/reader/recapture-diff.js`), comparison only. The hash and
the stored body are untouched.
- What is compared is the words, in order. A paragraph break is not
  one of them: when the two bodies' words are equal the banner stays
  down. Inside a real change, a run of changed paragraphs is split
  where both sides break after the same words, and a piece whose
  words are equal is shown as unchanged, so one corrected caption
  word marks its own stretch and not the whole re-cut transcript.
- A paragraph's leading time anchor is a position, not a word, in the
  three forms the transcript composers write.
- A header line that is nothing but a counted label and its number is
  noise. One word list now serves both orders, and `posts` joins it.

Second-guessable calls, each an INTERPRETATION with its default:
- Splitting or merging paragraphs without changing a word no longer
  raises the banner on any page, not only on transcripts. Default:
  keep. The banner's claim is that the words changed.
- A re-timed transcript (the same words, other stamps) is not a
  change. Default: keep.
- "3 posts" in prose is now noise, as "3 comments" already was.
  Default: keep.
- A paragraph that opens with a backticked clock time loses it from
  the comparison, transcript or not. Default: keep. Only the
  transcript composers write one.

The tests hold the comparison to what the composers write.
`composeMarkdownBody` is exported, and its output goes through the
reader's own HTML round trip before it is compared. A guard reads
every `toLocaleString()` count template under `src/shared/platforms/`
and fails when one is not noise; a count written any other way is
outside what it can see.

Left alone on purpose: the view count and the paragraph cuts still
move the canonical hash on every video re-capture, so the archive
still snapshots a prior version each time, and an audit anchored to
the earlier hash does not match the later capture. Taking the count
out of the hashed body changes what every later capture hashes and
publishes. That is its own decision, not part of a banner fix.

## 2026-11-16 — A test click sent before its listener was attached ran nothing and passed for a click

**Tags:** bug, tests, process

In a full `npm test` run on Windows, one `llm-job-consumers` test
(`links: a status poll dropped by a torn-down worker … is retried`)
failed once in nine runs: the links block showed an empty status 8 ms
into a test that takes about 2 s. The file passes every time when run
alone. Found during the issue #448 work and left for its own change.

**Cause.** `renderLinksBlock` (`src/portal/links-block.js`) appends
the Suggest links button, awaits `getCaseLinkRun` (an IndexedDB read),
and only then attaches the click listener. The test's `mountLinks`
polled every 5 ms for the button. When the read outlasted a poll, the
helper returned inside that window, and the stub's `dispatch('click')`
ran zero listeners and resolved at once. Nothing failed until an
assertion read a page the click had never touched. Holding every read
of the `case-link-suggestions` store for 25 ms reproduces it on
demand: all three `links:` tests fail.

**Fix, in `tests/` only.**
- `dispatch(type)` in `tests/helpers/page-stub.mjs` throws when no
  listener of that type is attached, and names the node. A click that
  would run nothing now fails where it is sent.
- `untilListening(root, text)` waits for the node and its listener,
  and says which of the two is missing when the wait runs out. The
  five mounts in `llm-job-consumers` wait with it.
- A fourth `links:` test holds the stored-run read for 25 ms, so every
  mount lands in the window. It asserts only that the click ran. With
  `mountLinks` put back on the button wait it fails every time.
- `tests/page-stub.test.mjs` pins the two stub rules.

The hypothesis and forensic blocks have no such window today: the
first wires its button before the button is reachable from the host,
the second appends and wires with no `await` between. Their mounts
wait on the listener anyway, so a later reorder cannot reopen the gap
quietly.

**Left alone: the product has the same window.** A click on Suggest
links between the button appearing and the stored-run read finishing
is dropped: no confirm, no status line. No person clicks that fast. A
scripted click (the browser smoke, an agent walk) could. Closing it
is a `src/` change — attach the listener before the read, or append
the button after it — and is not made here.

## 2026-11-16 — Seven tests failed only on Windows: Python checked out as CRLF, and URL pathnames used as file paths

**Tags:** bug, tests, process

Issue #448. On a Windows checkout (`core.autocrlf=true`) `npm test`
failed seven tests that pass on Linux CI. Two causes, neither in
`src/`.

**1. Two hash pins read working-tree bytes.** `.gitattributes` pinned
every shipped text type to LF but not `*.py`, so the 22 non-empty
Python files (the companion's 21 and the fixture generator) checked
out as CRLF. `tests/provider-normalize.test.mjs`
hashes `normalize.py` whole, and
`tests/direct-transcribe-deepgram.test.mjs` slices two functions out
of `deepgram.py` on `\n`; both hashed bytes the repository does not
hold. The fixture generator had the fault on one side too: it hashed
`normalize.py` with `read_bytes()`, so a fixture regenerated on such a
checkout pinned a hash CI cannot reproduce (observed: the CRLF hash
the JS test was computing). Its `deepgram.py` slice was already
immune, because `read_text` translates newlines.

Fix, both halves, as in the 2026-08-02 CRLF entry: `*.py text eol=lf`,
and the two tests and the generator undo the smudge (`\r\n` to `\n`)
before hashing. The attribute alone does not heal a tree that is
already smudged. Checked here: with the attribute in place the files
were still CRLF and `git status` was clean, so a branch cut before
this change stays red after it merges `main` unless the tests carry
the second half. To heal a tree anyway (this discards uncommitted
`.py` edits):
`git ls-files -z "*.py" | xargs -0 rm && git checkout -- "*.py"`.

What the reversal no longer sees: a working copy that differs from
its blob only by CRLF. That is checkout state, not a change. Python
reads CRLF and LF source lines identically, inside string literals
too, and with the attribute git stores LF whatever the working copy
holds. All 22 blobs were already LF, so no committed byte moves and
the fixture is unchanged; the edited generator reproduces it byte for
byte from LF sources and from CRLF ones.

**2. Five source guards built paths that only work on POSIX.** Four
(`entity-registry-store`, `local-key-store`, two in `llm-jobs`) took
`new URL('..', import.meta.url).pathname` as a filesystem path. On
Windows that is `/C:/…`, which `fs` resolves to `C:\C:\…`: `ENOENT`
before a single file was scanned. The fifth (`smoke-bundles`) made
its shell list repo-relative with `f.replace(REPO + '/', '')`, which
never matches a backslash path, so it compared absolute paths with
relative ones. All five now use the idiom `structure-guards` already
has: `fileURLToPath`, and `relative(ROOT, abs).split(sep).join('/')`
where a name is compared with a `'src/…'` literal.

No guard was loosened. Each was negative-controlled on Windows after
the change: a direct `Storage.set('entities', …)`, a
`LocalKeyManager.keys` touch, a retired message type as a literal, an
unlisted `runLlmJob({` call site, an HTML shell that loads no bundle,
one added line in `normalize.py`, one inside `_common_utterances`.
Each went red, and the five guards named the offender by its
`/`-separated path.

Left alone:
- `tests/smoke-selectors.test.mjs` strips `REPO + '/'` the same way,
  but only to shorten a path in a failure message. Its comparisons use
  `join()` on both sides.
- An eighth failure, seen once in nine full runs before any change and
  not a Windows fault in kind: `llm-job-consumers`' `mountLinks` waits
  for the Suggest links button, which `links-block.js` appends one
  awaited IndexedDB read before it attaches the click listener. A
  click dispatched in that window runs no listener and the test reads
  an empty status. With that read held for 25 ms in a throwaway copy
  of the test, all three `links:` tests fail. Its fix is a separate
  change.
