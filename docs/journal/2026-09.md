## 2026-09-05 — `(x || []).filter` is not an array guard: the known-unknowns block's stored-string crash

**Tags:** bug, pattern

Maintainer diagnostics, 2026-08-30, three occurrences: "Known-unknowns
block failed (f.primary_documents || []).filter is not a function".
One stored module-04 (source_quality) finding carried a STRING in
`primary_documents` — a record that predates or slipped past
`findings-schemas.js` validation — and `known-unknowns.js`'s
`(f.primary_documents || []).filter(...)` threw on it. `|| []` only
covers falsy values; any truthy non-array sails through, and the
portal block's catch-all removed the whole block. The one malformed
member cost the case every other member's unknowns, three times.

Fix is data tolerance, not a schema change (stored malformed records
must render degraded, never crash a block — the portal's own rule):
every list read in `shared/audit/known-unknowns.js` goes through
`Array.isArray(v) ? v : []`, every displayed scalar through a
string-only coercion (the renderer slices quotes), and the findings
payload is narrowed to a plain object. The same sweep covered
`shared/reference-resolver.js` — whose destructuring defaults cover
only `undefined`, so a string `primary_documents` iterated as
characters and an object would have thrown "not iterable" — and the
identical `moduleResults`/`findings` read in
`portal/references-block.js`. The renderer
(`portal/known-unknowns-block.js`) is untouched: it is a 1:1
projection of the model record, and the tolerance belongs at that one
seam, not duplicated in the DOM layer.

Tests: `tests/known-unknowns.test.mjs` (the hostile fixture — the
observed string plus every other list slot in a wrong-but-truthy
shape — beside a well-formed unknown that must survive, and a
no-drift check on the healthy shape), `tests/known-unknowns-block.
test.mjs` (drives the REAL renderer through a DOM stub and asserts
the block stays and shows the surviving unknown — the failure path
removes it, so an absent block is the observable crash), and the
resolver / references-block suites.

The pattern for future readers: **`|| []` is a null guard, not a type
guard.** Anything read from IndexedDB, chrome.storage, a relay event,
or a model's tool output that will be iterated or `.filter`ed needs
`Array.isArray` — the repo already does this in `article-pass.js`,
`entity-feed.js`, and the transcribe normalizers; this is the same
rule applied to the runs ledger.

## 2026-09-21 — The JOURNAL splits into monthly files

**Tags:** design, pattern

**Why.** The single newest-first `docs/JOURNAL.md` was the one file
thirty of the forty-five open-PR pairs conflicted on (RESET_PLAN §7
R0, "Split the JOURNAL now, not in R6"): every PR prepends its entry
at the same line, so any two of them conflict, and nothing else in the
reset could run in parallel until the file moved.

**The layout.** Entries live in `docs/journal/YYYY-MM.md`, one file
per month, OLDEST first; a new entry is appended at the BOTTOM of the
current month's file. `docs/JOURNAL.md` — the path every existing
citation names — is now the GENERATED index: newest first, grouped by
month, one line per entry linking to the entry's heading anchor, with
the tags when the entry has a `**Tags:**` line. `npm run docs:journal`
(`tools/gen-journal-index.mjs`: ESM, zero deps, no timestamp)
regenerates it; `tests/journal-index.test.mjs` fails the suite when it
is stale, when an entry is stranded in the index, when a monthly file
has a malformed heading or one dated outside its month, when a heading
repeats across files, or when a textual "JOURNAL YYYY-MM-DD" cite in
docs, skills, tests or source names a date with no entry. No markdown
link in the repo used a `JOURNAL.md#anchor`, so no link broke;
"JOURNAL YYYY-MM-DD" keeps meaning the entry of that date.

**The self-healing mover.** A PR that pre-dates the split still
prepends its entry into `docs/JOURNAL.md`. Both the monthly files AND
the index carry `merge=union` in `.gitattributes`: union on the index
means that prepend survives the merge instead of conflicting, and
every run of the generator first moves each such stray — an entry
heading in the index with its body up to the next `## ` heading, an
index marker, or EOF — into its month's file (created with the header
when absent, appended at the bottom, skipped when that heading is
already there), then regenerates. The drift guard makes forgetting
impossible: a stray or a stale index is red until the script runs.

**The migration was the script's first run.** With no
`docs/journal/` yet, all 246 entries were strays; the mover created
the five monthly files and appended them oldest-first. No entry was
moved by hand. Every entry's text is byte-identical to the old file
(heading through the last line before the next heading, trailing
whitespace kept) with one normalisation: the blank lines between
entries became exactly one. An independent re-parse of the old file
found 246 of 246 present verbatim and none extra. One consequence to
know: the ninety-odd relative links inside old entries were written
from `docs/` and now sit one directory deeper — left as they were,
because byte preservation was the contract; a follow-up may rewrite
them.

**Why order inside a file is not enforced.** Append-at-bottom is the
convention, but a union merge of two concurrent appends can
legitimately land them out of order, and that is not a defect: the
index sorts by date (newest first), then by file position. A guard
on ascending order would fire on a correct merge.

**The slug rule.** Index links use GitHub's heading-anchor rule
applied to the full heading text after `## `: lowercase; drop every
character that is not a letter, mark, decimal digit, connector
punctuation (`_` — GitHub keeps it), space or hyphen — so the em dash
and `§` go and "2026-09-15 — R0" becomes `2026-09-15--r0`; spaces
become hyphens; a repeated slug within one file gets `-1`, `-2`. The
R0 bullet's gloss omitted the underscore; the pins in the test say
which rule is implemented.

Provenance: INTERPRETATION (2026-09-21) — an agent artifact under
RESET_PLAN R0; the maintainer has not ruled on it.

## 2026-09-21 — The split's verifier found the mover deleting text; now it refuses

**Tags:** bug, design, pattern

**What the adversarial verification of the split found** (the same
day, against the four commits recorded in the entry above). Four
majors, two minors. A stray in the index whose heading was malformed —
hyphen-minus for the em dash, a one-digit day, a leading space, a CRLF
tail, month 13 — was neither moved nor kept: `extractStrays` left it
in `rest`, and `run()` overwrote the index with the fresh render. Exit
0, `--check` 0 afterwards. A contributor following "run `npm run
docs:journal`" deleted their own entry. A stray that AMENDED an
already migrated entry (same heading, different body) was dropped
behind one of 246 identical `skip … already has:` lines. Two green PRs
appending to the same month, each with a regenerated index, union
merged cleanly on main with the bullets in merge order while the
generator sorts newest-first — a stale index after a clean merge, in
about half the pairs by date order. And a branch from before the
split that merged main got a real conflict in `docs/JOURNAL.md`, with
no recipe anywhere a contributor reads. The minors: the forty-five
relative links that resolved from `docs/` and now sat one directory
too shallow, and a regex that took `2026-13-45` as a date and created
a legal-looking `2026-13.md`.

**The invariant that replaced the bug: the generator never discards
text.** Every line of the index is one of four things — residue the
regen reproduces or replaced (the GENERATED line, the markers, this
preamble or the pre-split one — `LEGACY_PREAMBLE`, byte-identical
across all 247 revisions of the old file — a month heading, a
bullet), a stray (moved), a duplicate of its migrated entry (dropped,
counted, one summary line), or a conflict marker (a boundary). Anything
else is listed by index line number, carriage returns made visible,
and the run writes NOTHING and exits 1; `--check` reports the same. A
stray whose heading exists in its month with a different body is
refused with both line numbers ("amendment NOT applied") and blocks
the write: the entry in the monthly file is the one to edit, then the
copy in the index is deleted by hand. The refusal is loud on purpose;
the alternative was a contributor's entry silently gone. Entry
headings now need a calendar date: the regexes take months 01–12 and
days 01–31, `isCalendarDate` adds days-in-month.

**Conflict markers are boundaries, because of a git subtlety worth
recording.** Git reads the `merge` attribute from the CHECKED-OUT
side. A branch from before the split has no union rule yet, so `git
merge origin/main` conflicts in `docs/JOURNAL.md`; `git rebase
origin/main` does not (the rule comes from the onto side) and lands
the old file, stray and all, after the index end marker as a union.
Deleting the three marker lines by hand and running the generator
worked, but the marker placement matters: git merges the two
preambles cleanly up to the Format block, so HEAD's side holds `---`,
the stray and every old entry, and theirs holds the "How to cite"
block, the markers and the bullets. Plain marker deletion would have
swept "How to cite" into the LAST old entry's body — and the new
amendment check would then have refused the very heal it was meant to
allow. So `<<<<<<<`, `=======` and `>>>>>>>` end a stray's body and
vanish, a diff3 base section is dropped, an unbalanced marker is
refused. Verified in a throwaway clone: the forward conflicted merge,
the rebase, and the reverse union each heal in ONE run of the
generator (1 moved, 246 duplicates, +7 lines against the split branch,
no marker survives, guards green). Both recipes live in CONTRIBUTING's
"Engineering journal" bullet and the `.gitattributes` comment.

**And the first real merge found one more.** When this branch merged
`main` after the R0 net landed, the union kept the net's three entries
in the index — and the mover refused all of them, reporting 26 old
entries as "amendments". They were not: the link rebase one commit
earlier had moved every relative link in the monthly files one
directory deeper, so the untouched copies still in the old
`docs/JOURNAL.md` compared unequal. The verifier's simulations ran
before that commit and never saw the interaction. The mover now
rebases a stray's links on the way in — a moved entry's links resolve,
and an original-depth copy compares equal — with a lab test that pins
both halves. A generator that moves text between directories must
move the text's own relative paths with it; "byte-preserving" was the
right contract for the migration and the wrong one for the mover.

**Why `main` cannot carry a stale index, and the bot that was cut.**
The verifier's U1 simulation: two PRs each append to the same month
and each regenerate the index; a clean union merge keeps the two
bullets in merge order while the generator sorts, so about half the
date orders leave the merged tree with a red drift guard. The first
repair answered with a push-to-`main` workflow that regenerated and
committed after every journal merge. It was cut before this PR opened,
for three reasons: `main`'s branch protection requires a pull request,
so a `GITHUB_TOKEN` push to it fails; a bot that writes to `main` is
persistence the maintainer never asked for (the hygiene cron is
report-only for the same reason); and the case it guarded cannot
reach `main` under the protection already in force — an up-to-date
branch is required before merge, so the second PR merges `main`
first, its CI runs the drift guard on the merged tree, and a stale
index is red there, one `npm run docs:journal` from green. What the
`.gitattributes` comment now states is that residual: union on the
index buys a red drift guard for a conflict, never silent wrongness,
and if the protection is ever relaxed the same guard goes red on
`main`'s own push CI.

**The link rebase, and one deviation from the verifier's cut.** The
migration commit preserved every entry byte-for-byte, so this is the
follow-up the split entry promised: every relative repo-path link
gained one `../` — 97 lines in the four older monthly files. The
verifier proposed rewriting only the forty-five that resolved before
the split; the rewrite here is uniform, because the editor-style
`path:line` references were repo paths written from the same place and
half-rebasing them would have left `docs/src/…` paths beside
`../../src/…` ones. The guard strips `#fragment` and `:line` before
resolving, and its shrink-only allowlist holds the four targets that
were dead before the split (the removed popup surface, the retired
userscript migration) instead of fifty-seven link sites.

**Deliberately unchanged.** Order inside a monthly file is still not
enforced (a union of two appends may land them out of order; the
index sorts). A genuine body line shaped exactly like an index bullet
is still dropped from a stray — a stated limit with a very specific
shape, not a silent one. Independent re-check after the repairs:
246 of 246 original entries present verbatim (the rebase applied to
both sides), each exactly once.

RESET_PLAN R0; the maintainer has not ruled on it.

## 2026-09-07 — The browser smoke joins CI: `npm run smoke`, a pages check, the MA.6 walk un-rotted — and the review that found the first cut green-while-wrong

**Tags:** design, pattern, bug

**The friction, cited.** `tools/smoke/ma6-walk.mjs` — the one observer
of the layer no unit test executes (built bundles loaded as a real
unpacked extension) — was run by nothing: no npm script, no
devDependency, container-only absolute paths, and a selector that
matched heading copy (`/Extracted assertions/`). UA.3 renamed the
heading on 2026-08-12; the walk was observed red on its own selector
on 2026-09-05 while every product check inside it still passed.
Meanwhile the 2026-08 record shows eighteen "suite green, behavior
wrong" escapes, fourteen of them shaped navigate / click / read DOM —
the class this walk observes (`docs/RESET_PLAN.md` §6, R0; the
verification lens in `docs/audit-2026-09-05/`). The soak rule was
carrying all of that on one person's browser.

**What landed.** `playwright` as an exact-pinned devDependency (the
browser revision rides the version). `tools/smoke/lib/browser.mjs`
resolves the full Chromium (`XR_CHROME`, else Playwright's own — the
headless_shell build cannot load extensions), launches the unpacked
extension on a throwaway profile with egress killed at the browser
level (every launch proxies non-loopback traffic to a dead loopback
port), reads the extension id off the service worker, discovers the
extension pages from the HTML shells in `src/`, reads the bundle list
from the `configs` `esbuild.config.mjs` now exports (the build runs
only as the entry script), and bundles seed harnesses into `dist/`,
sweeping them before, after and on exit. Two scenarios. `pages`: after
proving its own observers on a canary page (an uncaught throw and a
`[X-Ray]` console.error on `about:blank` must both be seen, or exit 2),
it opens every page and waits for the page's READY STAMP —
`<html data-xr-ready="<page>">`, set by each page as the last act of its
init through `markReady()` in `src/shared/smoke-anchors.js` — then fails
on any uncaught exception, any product `console.error` (`[X-Ray`, the
`Utils.error` prefix) or failed local resource (`net::ERR_`), or an
empty body. `ma6`: the existing walk, anchored on the SHARED constant
`SMOKE_ANCHORS.extractionBlock` (the renderer sets it from the same
table), waiting on the block and on the publish status line instead of
sleeping, verifying the relay pin by read-back, and failing on every
uncaught exception and every product console.error except the one it
provokes on purpose. `tests/smoke-selectors.test.mjs` pins the seam
(every table value is set in `src/`, comments stripped, consumer
selectors excluded, any other spelling banned);
`tests/smoke-bundles.test.mjs` pins the built set to the loaded set
(manifest + shells + `getURL()`), both ways. `tools/smoke/run.mjs` runs
each scenario in its own PROCESS GROUP — SIGTERM on timeout, SIGKILL
five seconds later, the group so a hung Chromium dies with its scenario
— sizes the per-scenario timeouts (90 s + 180 s) under the 300 s
budget so an advisory timeout can never fail the run through the
budget line, scans every output file for key material before it
uploads, and treats an empty selection or an unknown flag as a usage
error. The CI job `browser-smoke` runs on a PINNED `ubuntu-24.04`,
installs Chromium, runs `npm run smoke -- --advisory=ma6`, and uploads
screenshots and reports as an artifact. The THREAT_MODEL gained the CI
surface and its written invariant (never a `release.yml` dependency,
never a secret).

**The review round, and why it is the point.** The first cut passed
its own checks and CI (81 s). An adversarial review (three lenses,
thirteen verified findings, `docs/RESET_PLAN.md` §12's method) then ran
negative controls on it and found the gate GREEN-WHILE-WRONG in exactly
the class R0 exists to catch: an emptied `portal.bundle.js` passed
(`157 chars, 0 console errors` — the shell's static text), a misspelled
`<script src>` passed (a missing resource is a console error, not a
`pageerror`), and a caught init failure routed through `Utils.error`
was reported, never failed on. The runner's "hard timeout" could not
end a scenario whose Chromium was hung, because Playwright's SIGTERM
handler awaited a `Browser.close` that never answered. "Nothing reaches
the network" was an argument from the empty profile, not a control.
The bundle list was scraped from the config's text and dropped all five
page bundles under an ordinary refactor while still returning a
non-empty list. The guard test counted a commented-out anchor as a
definition. The throwaway profile — holding a generated nsec — was
never deleted. Every one of those is now closed and has a negative
control on the record: empty bundle → red ("no ready stamp"),
synchronous throw → red, `[X-Ray]` console.error then stamp → red,
misspelled script → red; a detached child that ignores SIGTERM and
holds a grandchild dies by group SIGKILL after the grace period;
`https://relay.damus.io` and `http://example.com` fail with
`ERR_PROXY_CONNECTION_FAILED` while `ws://127.0.0.1:1` is refused in 2 ms
unproxied. A second round on the fixes then found the profile deletion
covered only the clean exit (35 leaked profiles on the dev machine,
eight holding a key), the egress kill was a launch flag nothing
observed, the build's new main guard was false under a symlinked
checkout (Node realpaths the ESM main; `npm run build` would have
exited 0 producing nothing), the ready stamp was fail-open (a shell
could carry it statically), a stale `dist/` passed `assertBuilt`, and
the discovered page list could shrink silently. Closed in turn: a
synchronous exit hook plus a runner sweep for profiles; an egress

carries `data-xr-ready`, every page entry calls `markReady('<dir>')`
exactly once and nothing else does, every shell under `src/` is a
discovered page, and `dist/` is newer than `src/`. The pattern, twice:
a harness's own checks cannot tell it what it does not observe; only a
control that SHOULD go red can — and a control stated in a document is
a claim until something observes it.

**Second-guessable calls.** (1) `pages` gates from day one; `ma6` is

## 2026-09-05 — Corpus reduce lost a ~$5 Fable run: the long LLM passes become JOBS

**Tags:** bug, design, external

**Report (maintainer, 2026-08-30).** Portal: *"Synthesis failed: A
listener indicated an asynchronous response by returning true, but the
message channel closed before a response was received."* An 87-member

**Root cause.** `xray:llm:corpus-reduce` (and `corpus-map`,
`entity-page`) each held ONE `chrome.runtime` message open across the
whole Anthropic call: `return true` + an async `sendResponse`. MV3 kills
a worker whose **single request runs past ~5 minutes** — a separate rule
from the 30-second idle timer that the 2026-07-18 keepalive fix
addressed. The page's 20-second pings kept the worker *idle-alive* and
could not help: the request itself was the thing over the limit. When
the worker died, the in-flight fetch died with it; and even had the
fetch finished, the result existed only as the argument to a
`sendResponse` on a dead channel — nothing was persisted before the
response hop. (The 2026-07-18 entry's "my 420s → teardown proved it"
was this rule, misattributed to idle.)

**Fix — the in-tree job pattern** (`xray:transcribe:{start,status}` is
the precedent), now `shared/llm-jobs.js` + `xray:llm:job:{start,status,
find,ack}`:

- `start` answers with a job id **immediately**; the worker runs the
  pass detached. No request ever waits on the model.
- The RAW result is written to `chrome.storage.local` under
  `xray:llm-job:<pass>:<scope>` **before any response hop** — the
  running record lands first, the done record strictly after (ordered,
  never raced).
- The page long-polls `status` (≤15s a message, clamped at the
  receiver). A poll after a worker restart reads the persisted record;
  a dropped poll is retried without a second start. **A dropped channel
  costs a refresh, never a re-spend.**
- Jobs are scoped: the reduce by `caseId:inputHash`, the map by the
  extract's content-only cache key, the entity page by
  `entityId:inputHash`. A start whose scope has a **running** job
  attaches to it; one whose scope has a **done, successful, un-acked**
  result reuses it — the pass is not invoked. The page `ack`s (deletes)
  only after ITS persist (`saveCaseBrief`, `saveCorpusExtract`,
  `saveEntityPage`). Failed / lost / unsuccessful records never replay.
- While a job runs the worker **heartbeats its own record** every 20s —
  a `chrome.storage` write is an extension API call, which resets the
  idle timer from inside the worker — so a job outlives a portal reload
  gap the page-side keepalive could not cover. Bounded by the pass's
  own AbortController timeout; a job can never hold the worker past the
  call it was started for.
- A `running` record no live worker knows (the registry is per worker
  instance) reads as **`lost`** — the one case that IS a re-bill, and it
  says so.
- Records are **workspace-scoped** (`xray:llm-job:<ws>:<pass>:<scope>`),
  the workspace resolved at the receiver from the active-workspace
  pointer, never taken from the message — the security-threat-modeler
  review's one finding: a global record would have let a case bundle
  imported into two workspaces (same ids, same members) serve
  workspace A's brief — with A's dossier digest — to workspace B.
  Every other piece of casework state is workspace-isolated; this one
  is too.

## 2026-09-25 — A failed read erased the entity registry: `entities` writes now follow the keystore's discipline

**Tags:** bug, security, pattern

The follow-up #392 named. Every `EntityModel` mutator, and the
entity-sync pull's two registry phases, read `entities` with the
fail-open `Storage.get`, which returns `{}` for a read that FAILED as
well as for one that found nothing, and then wrote that snapshot back
with its own change. One failed read in `create`, `importRecord`,
`importForeign` or the pull's record phase erased every other entity
record (their keys survived). A failed read in the pull's planning
phase let a STALER pulled key replace a local one. In `update`,
`linkAlias`, `delete` and the publish stamps it surfaced as "Entity not
found" or a silent no-op, and in `restoreDerivedKeys` as "Nothing to
restore". Two pages writing the registry lost each other's writes, the
lost update #392 fixed for `local_keys`. And a failed read of the
workspace POINTER became 'default': cached, so a page that hit one and
then ran a reset cleared the DEFAULT workspace; read afresh by a
restore or merge, so one whose own read failed wrote the file into the
DEFAULT workspace.

The fix extends #392's discipline to the registry. `withStoreLock` and
`lockedReadModifyWrite` (generalized in place in
`local-key-manager.js`, each store's one lock fixed in `STORE_LOCKS`)
now serve two stores. Every registry write is a read-modify-write of a
FRESH strict read under the Web Lock `xray.entities`, with the same
extension-origin refusal; async preparation runs before the lock. The
pull plans with `EntityModel.readRecordsStrict` and writes with
`mergePulledRows`, comparing the pulled record's own `updated` (0 when
absent). The backup restore and merge read the whole storage area
strictly (a failed read had made a merge write the file's registry over
the local one), and the reset's safety backup reads each key strictly.
Restore, reset and removal nest the registry lock inside the keystore
lock; the merge takes only the registry lock; nothing takes them in the
other order.

The pointer: **ONE cached pointer per page.** Every read and write —
plain and strict `Storage` calls, the locked writes, the keystore Map
and `signEvent`, `EntityModel.get`/`getAll`, the IndexedDB names and
the LLM-job scope — resolves the workspace through `storage.js`'s
cache, with origin/main's rule: a failed pointer read is 'default',
cached until the pointer next changes. `workspace-keys.js`'s
`activeWorkspaceId` (the IndexedDB names, the LLM-job scope) now
defers to that cache once `storage.js` loads; on main it read the
pointer again, uncached. Four rules keep that one pointer from ever
giving a page two answers (and a fifth, for what a page holds across
a switch):

- **Single flight.** Callers that find the cache empty share ONE read.
  Every pointer change empties it, and the keystore's listener and any
  page code that re-renders on the change each used to start their own
  read; one failed read among them left one page holding two
  workspaces (the verifiers' erase2 probe: a plain read-modify-write
  carried the default workspace's claims over the active one's; the
  race probe: a record shown and signed with the other workspace's
  key; probe S4, which landed either way from run to run on main, now
  lands the same way every run). A read that started before a switch
  never fills the cache after it.
- **The keystore Map answers only for its own workspace.** The Map is
  data loaded under a pointer, and a failed refresh keeps the last good
  one (main's rule). It now records the workspace it was loaded under,
  and `getKey`/`listKeys`/`signEvent` serve nothing while the page's
  pointer names another — after a switch whose keystore read failed,
  and in the moment between any switch and its refresh. Before, the
  new workspace's records were shown, signed, pushed and bundled with
  the previous workspace's private keys (probe P1; main too). So
  WITHIN ONE `get`/`getAll` call a record is paired only with its own
  workspace's key (relying on storage answering reads in the order
  they were made).
- **A step of an operation planned in one workspace is never redone
  in another.** A locked write redoes itself when the pointer moves
  under it (#392's rule), which is wrong when the caller planned
  outside the lock. `EntityModel.create`, `delete`,
  `restoreDerivedKeys` and the sync pull pass the workspace they
  planned in, and a step that finds another is refused; so do
  `importRecord` and `importForeign`, and the case-bundle import pins
  one workspace for every key and record it writes (`importKey` and

- **Destructive wholesale operations verify.** The reset, workspace
  removal, backup restore / merge / export and the reset's safety
  backup first re-read the pointer strictly
  (`Storage.verifiedWorkspaceId`) and refuse with a
  `StoreRefusedError` — nothing written or downloaded — when that read
  fails or disagrees with the cache. They then re-verify right before
  each later step that resolves the workspace through the cache (each
  database a restore, merge or export fills or dumps, each key the
  safety backup reads, each key the reset deletes, the restore's and
  merge's storage phase under the locks), in the same microtask chain
  as that step, so each of those steps acts on the verified workspace
  or the rest is refused. Two kinds of step are NOT re-verified: the
  version pre-checks (`collectDbVersions` in the export,
  `assertBackupNotNewer` in the restore and merge) open each database

  cleared the OTHER workspace's databases, and an export or safety
  file mixed two workspaces (probes P2c, P4d, P6; main too). A merge
  reports each database it did not merge beside what landed, and the
  restore and merge now reject a raw storage remove or write that
  fails (a restore had reported success over a workspace it emptied).

  safety file names its workspace (a new `workspace` field; nothing
  reads the file back), and the reset, when handed it (Options does),
  refuses any other.
- **What a page holds across a switch is refused, not re-paired.** A
  record read before another page's switch and signed after it gets a
  refused signature, never a wrong one: `signEvent` refuses a key that
  does not hold the event's `pubkey` ("Key mismatch: <keyName> does not

  read in one workspace was signed with the key the other workspace
  holds under the same name (probe T7; main too). The case bundle,

  produces no file (`StoreRefusedError`, "the workspace changed
  mid-bundle — no file") if the pointer moved at any point while it
  was collected (`Storage.workspaceEpoch`, which moves with every
  pointer change); before, a switch mid-collection shipped the other
  workspace's private key in this case's bundle (probes T5, T6 and the
  case-bundle probe; main too).
