# The librarian, the commons, and the embeddable record (kickoff seed)

**Status: SEED — captured 2026-08-23 from the maintainer's direction,
verbatim in intent. Not started, not approved, no slices.** This
document exists so the direction is not lost; it becomes a real kickoff
only after the discipline passes below run. The maintainer's own
framing: "That might be a larger discussion for later that requires
substantial planning."

## 1. The direction, in the maintainer's terms

- **X-Ray should act more like a librarian.** Case bounding is
  "helpful for usability and focus," but articles need to be available
  to more than one case, and switching cases needs to be figured out
  properly rather than remaining a namespace jump.
- **NOSTR artifacts must be genuinely usable and buildable-upon by more
  than one person/npub.** The social mechanics need thinking through,
  and "it will be critical to make it clear to everybody how it works.
  It needs to be both useful and usable."
- **The governing design philosophy: value at N=1 through N=∞, and
  everywhere along the way.**
- **Corpus analysis is the flagship shared artifact** — "the most
  wikipedia-like artifact that X-Ray creates." Two named requirements:
  it must work against MULTIPLE cases, and its ITERATING VERSIONS must
  be visible ("if I run corpus analysis we can see the iterating
  versions of it"). It "needs to be accessible and useful by the
  correct people," and — for now — "useful and usable by more than
  just me."
- **Privacy and private knowledge bases come later**, but the design
  must not foreclose them.
- **Substack embedding:** it must be easy to embed NOSTR knowledge
  tidbits inside Substack writing — extra value without inlining the
  content, especially because "its provenance is generated by AI, and I
  want it to be a wikipedia-like resource that can be referenced."
  Provenance legibility is a requirement, not a nicety.

## 2. What already exists (so the discussion starts from facts)

- **Multi-case membership already exists INSIDE one workspace.** Case
  membership is tag∪claim (`shared/case-membership.js memberUrlSets`) —
  an article tagged into two case alias-families is a member of both.
  The real constraint is one level up: **workspaces are storage
  namespaces bound to one case each** (`Workspaces.activate` moves the
  namespace and the signing identity together, and switching reloads
  the page). In practice case = workspace = silo, which is exactly the
  librarian tension: the same article cannot serve cases in two
  workspaces without re-capture.
- **Corpus analysis today:** the case brief lives locally
  (`xray-audits` v2 `case-briefs` store) and publishes as `30023` +
  kind `30068` CaseBrief (`corpus-publish.js`). `30068` is
  parameterized-replaceable — **relays keep only the latest version per
  address**; older versions survive locally in the event journal. The
  "visible iterating versions" requirement therefore touches wire
  design: version-carrying tags, a non-replaceable revision kind, or a
  documented reliance on local journals are all candidate shapes, each
  with compat consequences (`ecosystem-pm` owns that call).
- **The N>1 seam already exists:** the Phase-25 network client does
  follow-by-npub, pull-not-live feeds, and incorporate-as-PROPOSALS —
  the human-accept boundary that any multi-npub building-upon should
  probably generalize rather than bypass.
- **Entity pages** (user-signed replaceable `30023`) are the closest
  existing thing to the wikipedia-like artifact and share the same
  versioning question.
- **Embedding primitives:** published artifacts have NOSTR addresses
  (`naddr`/`nevent`); web gateways (e.g. njump-style) can render them at
  a URL a Substack post can link. TRUE embedding (cards, excerpts,
  live-updating tidbits) is unbuilt and needs its own design — including
  how AI provenance is displayed at the embed surface, not just in the
  event tags.

## 3. The questions a real kickoff must answer (not here)

1. Librarian model: what is the unit of sharing across cases — the
   article row, the workspace, or a new library layer under both? What
   happens to signing identity when content crosses case boundaries?
2. Case switching as a first-class UX rather than a namespace reload.
3. Social mechanics for multi-npub building-upon: who may revise what,
   how disagreement renders, and how it is made legible to a newcomer
   ("clear to everybody how it works").
4. Corpus analysis across N cases: inputs, keying (the corpus-v7+
   one-extract-per-article layer is already case-free — the REDUCE is
   not), and spend.
5. Version visibility for briefs/entity pages: wire shape + UI.
6. The embed story for Substack (and by extension the open web), with
   AI-provenance display as a hard requirement.
7. The privacy/private-KB posture that must not be foreclosed now.
